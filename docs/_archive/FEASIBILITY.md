### 4.4 版本識別陷阱 ⚠️

新版 POR 封面／目錄仍然寫住 **「2010 版」**（見 `out/por_2026.markitdown.v2.md` 第一個 chunk）。

即係：**兩份內容唔同嘅 PDF，版本標籤完全一樣。**

→ 絕對唔可以用封面文字做版本識別。必須用 `sha256` + `Last-Modified` + PDF `creationDate`。
→ 你嘅 MD frontmatter 入面 `version:` 欄位如果填「2010版」，等於冇填。應該填 `2010版 (rev 2026-09-17, sha256:03381e0c…)`。

### 4.6 對 pipeline 設計嘅修正

原本 DESIGN.md 假設「政策檔案會原地更新」。實測證明實際行為係：

> **新版本 = 新檔名（`por_c_20220908_1.pdf` → `POR_C_20260917.pdf`），舊 URL 保留不動。**

所以：
- ❌ 對固定 URL 做 ETag polling **捉唔到版本更替**（舊 URL 永遠回 304）
- ✅ **必須以官方 listing 頁為 primary source of truth**，parse `<a href$=".pdf">`，發現新檔名 = 新版本
- ✅ ETag polling 只做 secondary（捉「同一 URL 原地改」嘅少數情況）
- ✅ 一旦偵測到新檔名 → 舊 MD 即標 `status: superseded` + `superseded_by`
- ✅ 額外監控：舊 URL 係咪仲 live（如果 live，就要喺自己嘅站主動聲明「呢份已過時」）

## 6. 「由自用 → 所有人用」嘅分層路線（你話未有 DB 方向）

| Tier | 對象 | 架構 | 成本 | 你要處理嘅新問題 |
|---|---|---|---|---|
| **T0** 自用 | 你一個人 | MD repo + Gemini Notebook / Claude Project<br>（免費版每本 50 個來源、每來源 50 萬字）[1](https://fast.io/resources/notebooklm-file-size-limit/) | $0 | 幾乎冇 |
| **T1** 旅／區 | 幾十人 | **靜態站 + client-side search**（MkDocs Material / VitePress + Pagefind / MiniSearch）<br>由 MD repo 直接 build，GitHub Pages 免費托管 | $0 | 唔需要 DB！全文搜索已夠用 |
| **T2** 旅／區 + 智能問答 | 幾十至幾百人 | T1 + 一條 RAG endpoint（serverless function + SQLite-FTS5 / LanceDB / Supabase pgvector） | ~$0–20 USD/月 | 引用、免責、guardrail、rate limit |
| **T3** 地域／總會級 | 全港 | T2 + 權限分級 + audit log + 正式授權 | 需要立项 | **合規、Sensitivity 分級、SLA、內容責任** |

### 我嘅建議：T1 先做，因為佢 CP 值最高

好多人一諗「俾所有人用」就跳去向量庫 + LLM。但你嘅內容係**規條式文件**，用戶其實多數想「搵到原文」多過「要 AI 幫我諗」：

- 靜態站 + 全文搜索：準確度 **100%**（因為直接顯示原文），零幻覺，零成本，零合規風險
- Git Action 每日偵測更新 → rebuild 靜態站 → 自動 deploy。**呢個先係「同樣方式」嘅最直接用法的**
- 之後先喺同一份 corpus 上加 RAG 問答（T2），兩個功能共用一份 MD

**即係話：你唔使即刻決定 DB 用乜。MD repo + 靜態站已經可以「讓所有人使用」，而 DB 只係 T2 先需要。**

## 8. 下一步：點樣真正量度「準唔準」

以上全部係 **轉換質素** 嘅量度。你真正想知嘅係 **問答質素**，而呢個只有一個方法可以答：

**建一個 20–50 條嘅測試集（golden set）。**

格式：
```json
{
  "q": "樂行童軍團最少要幾多名團員？",
  "expected_doc": "POR",
  "expected_rule": "2.3.7(e)(i)",
  "expected_answer_contains": ["六名"],
  "note": "注意 2025-08-01 修訂只改年齡，人數未變"
}
```

有了呢個，你可以：
- 客觀比較 MarkItDown vs 其他 extractor
- 客觀比較「有冇做 post-process」
- 客觀比較「有冇做通告 cross-link」
- 每次 CI 跑完自動 report 準確度，退化就 block deploy

**我建議測試集來源：搵 3–5 位領袖，叫佢哋寫「過去一年真係查過／問過」嘅問題。** 唔好自己幻想問題 — 真實分佈先有意義。

### 10.1 兩個工程伏位（實測發現）

1. **大小寫敏感**：官方目錄頁寫 `POR_C_20260917.pdf`（大階），直接 HEAD 呢個 URL 會 **301** redirect 去 `por_c_20260917.pdf`。Registry 必須跟 redirect 並 normalize 做 lowercase。

### 呢個表就係成個項目嘅存在理由

任何人今日問任何 AI「幼童軍幾多歲」，AI 做 web search 有大機會攞到 2022 版 PDF（官方域名、URL 正規、搜尋排名高），然後答「足七歲半至足十二歲」—— **差成一年半**，而且附埋原文引用，睇落完全可信。

**5/5 個支部都錯。** 唔係個別 case，係系統性。

### 11.1 POR 係「經整合嘅活文件」

新版 PDF 內部有 inline 修訂日期戳，分佈由 2012-05 一直到 **2026-09**（16 個唔同月份）。即係通告修訂會被併入主體。

→ **好消息**：POR 嘅準確度可以靠主體本身保證，唔使逐張通告 patch。
→ **通告 crawler 嘅角色要重新定位**：(a) 捉最新一次修訂（主體 PDF 有 lag）；(b) 覆蓋唔喺 POR 入面嘅政策（訓練綱要、青少年活動政策、Safe from Harm、各署指引）。

## 13. 定位修正：呢個係 aggregator，唔係 authority

用戶嘅定位（已採納）：

> 我唔係重寫、唔係話總會嗰份錯。我係把**已經公開、網上搵到**嘅檔案，整理成方便 AI 讀取嘅格式，
> 避免成員搵錯舊資料。
> 「本網站為非官方獨立工具，旨在方便成員瀏覽公開資訊，與香港童軍總會無任何官方從屬關係。
> 所有通告版權歸香港童軍總會所有。」

呢個定位令成件事簡單好多，因為：

| 唔使做 | 使做 |
|---|---|
| ❌ 唔使判斷總會邊份文件「錯」 | ✅ 只陳列事實：官方目錄頁而家列緊邊份 |
| ❌ 唔使自己做權威解讀 | ✅ 每條結果回官方原文連結 |
| ❌ 唔使改寫內容 | ✅ verbatim 逐字引用 + sha256 + 檔案日期 |
| ❌ 唔使承擔內容責任 | ✅ 當眼聲明 + 「以總會最新公佈為準」 |

**版本核對功能完全喺呢個定位之內** —— 佢只係講「官方目錄頁而家列嘅係呢份」，呢個係可驗證嘅事實，唔係價值判斷。
